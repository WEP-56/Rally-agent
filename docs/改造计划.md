## 1. 目标与边界

### 1.1 v1 必须做到

- 主对话可流式对话、可中断、可中途插话（steer）；永续单对话，压缩后任务清单与记忆不丢（Q11/Q23）。
- 主 agent 能派任务到工位；任务在右栏默认可见；状态含待批准、排队（含原因）、进行中、需处理、完成、失败、无需处理、已取消（[01 §3](superagent/01-角色与协议.md)）。
- worker 在关键节点汇报时自动唤醒主 agent；worker 的问题与不可逆请求由主 agent 依原话处理，否则上升用户（Q3/Q8/Q24）。
- 长命令自动转后台作业，dev server 以服务登记、可在内嵌浏览器预览；内嵌终端供用户使用（Q14/Q20）。
- 工具调用在主对话与工位都以统一卡片呈现（含 diff、输出、退出码、耗时）。
- 不可逆动作有且只有一个确认入口；有一次明确确认；有审计行。
- 右栏可查看每个任务的访问痕迹（读/写文件、网络域）。
- Windows 单实例、崩溃后可恢复、进程树可终止。

### 1.2 v1 明确不做

- 不做多用户/多租户、不做云同步、不做加密存储（C3）。
- 不做权限系统/角色/策略引擎；门控仅为可逆性三档（C5）。
- 不做跨平台抽象（仅 Windows，C3）。
- 不引入 Pi `durable` 包（仅参考其 checkpoint 思路）。
- 不内嵌 dsh 运行时（只借鉴字段与状态命名）。
- 不做改动回滚（Q21：改坏了由用户自己用 git）；不设任务预算上限（Q12，只做用量可见）。
- 不做 worker 角色/类型，不允许 worker 嵌套子 agent（Q13/Q15）。
- 不内置浏览器自动化/computer use，交给用户自行配置 MCP（Q19）。
- 不显示进度百分比与阶段名，只显示粗略状态＋时间（D8/Q16）。
- 右栏不做任务交互（Q18）；不做"新对话"（Q11）。

## 2. 总体架构（【建议默认】）

```
Electron main（Node）
├─ Supervisor（Rally 自建）
│  ├─ TaskStore：任务/运行/输入/问题/门（JSONL 事件＋快照，单写者）
│  ├─ EventBus：单事件流，信封 {seq, ts, taskId?, runId?, sessionId?, type, payload}
│  ├─ Scheduler：审批、依赖、名额（默认 2，另有 1 个用户唤醒额外名额）、写锁（C10）
│  ├─ SessionPool：主会话（永续、物理分段）＋每任务一个 worker 会话
│  ├─ RelayQueue：worker → 主 agent 的中继与通知（有序、幂等、合并唤醒）
│  ├─ GateService：外门（派发审批，全局开关）＋内门（不可逆，原话依据）＋超时＋审计
│  ├─ JobManager / ServiceRegistry：后台作业与常驻服务（Q14）
│  ├─ AccessTrace：按任务聚合 fs_read/fs_write/fs_delete/net
│  └─ MemoryStore：MEMORY.md（Q23）
├─ Pi 内核（改造后的 packages/coding-agent）
│  ├─ AgentSession / tools / extensions / system-prompt
│  └─ tool_call 钩子 → GateService／只读模式检查／任务结束后拒绝
├─ 内嵌浏览器（WebContentsView）与终端（xterm.js＋node-pty）（Q20）
└─ IPC（typed channels）→ Renderer
   └─ React 双栏（左主对话 / 右只读标签页，同一事件流的两个 selector）
```

**【事实】** Pi 已有 `AgentSession`、会话树 JSONL、`tool_call` 阻断钩子、`src/modes/rpc` 与 `src/modes/json-event.ts`；Electron 侧直接复用 Pi 内核，不自建 agent 循环。

**【建议默认】** 主进程持有所有 session（不在 renderer 里跑 AgentSession），renderer 只消费事件与发命令；崩溃恢复与进程终止都在 main。

**【已定】** 任务层与事件流使用 **独立 JSONL + 全局单调递增 `seq`**；任务写入必须**单写者**（统一写入通道串行化，多写者会让 JSONL 烂掉）；事件顺序必须**先落盘再广播**，事件信封带 `taskId`；重放以 `seq` 为唯一序。

**【已定】** 并发上限默认 **2**（C6）。调度语义：可运行任务数达到上限时，新任务进入 `queued(waiting: capacity)`，与 `queued(waiting: dependency)` 共用同一状态、UI 文案区分"等待名额 / 等待依赖"；任一任务结束即补位。v3 补充：排队原因增加 `write_lock`（C10）与 `dependency_failed`（Q9）；用户发起的唤醒可以使用 1 个额外名额（[04 §3](superagent/04-工作区与并发.md)）。

**【事实/推断】** 资源影响：每个并行 worker 都是一份独立的模型上下文（独立 `AgentSession` + 独立会话 JSONL），并发 2 即约 2 份上下文与 2 路 API 请求；上限调高会线性增加内存、token 消耗与限流风险，**不会**因为共享主对话而摊薄。**【建议默认】** 设置项上限暴露给用户，但默认保持 2，并在设置页标注"每增加 1 路约增加一份上下文成本"。

## 4. System prompt 契约

v3：提示词的组装顺序、优先级、英文初稿与消息模板见 [03 提示词](superagent/03-提示词.md)。本节只保留契约摘要。

### 4.1 主 agent 行为契约

| 契约 | 要求 | 反例 |
| --- | --- | --- |
| 首句回应 | 收到请求的第一句明确"我在做什么/先做什么"，不先长篇分析 | 直接输出十段方案 |
| 派发回执 | 派任务后回执：`taskId`、标题、一句话说明、依赖；待批准时说明"等你批准"。不含验收标准（Q4） | "已经安排好了"但无 ID |
| 只在需要时发言 | 结果可用或需要用户行动时才发言；普通进展不播报（Q3） | 每个工具调用都汇报一次 |
| 结果转述 | 1–3 句讲"用户现在能用什么"；改动与证据由系统从访问痕迹汇总，留在任务页（Q10） | 把 worker 流水账复制进主对话 |
| 来源标注 | 引用文件写路径，引用网页写域名/URL，引用任务写 `taskId` | "我查过了" |
| 不夸大 | 任务"完成"只因 worker 汇报 ready；未运行、未验证、被门拦住的动作必须写明 | 把"准备做"说成"已完成" |
| 原话依据 | 派发、追加、代答、放行、取消、续接、写记忆都要引用用户原话；没有依据就问用户（C8） | 主 agent 凭判断替用户拍板 |
| 不越界 | 只读工具只用于理解意图与回答小问题；不替 worker 调查技术问题（C7） | 主 agent 自己读日志定位 bug |

### 4.2 对 worker 的约束

- 需求只来自简报里被引用的用户原话；主 agent 的备注只是背景（Q4）。
- 不能直接找用户；问题通过 `task_report` 提出，由主 agent 依原话代答或转给用户（Q8）。
- 汇报状态：`progress`（可带问题）、`ready`、`blocked`、`failed`、`dropped`；没有阶段名与百分比（Q16）。
- 结束汇报写结论、检查方式、未完成项；改动文件由系统补齐（Q10）。
- 只读任务不改产出目录以外的文件；不主动 commit/push（Q6/Q21）。

### 4.3 注入位置（【事实】）

- Pi `core/system-prompt.ts` 支持 `sections`、`customPrompt`、`appendSystemPrompt`（`:9-77`）。主 agent 不加载 Pi 编码基础提示词与项目 `AGENTS.md`；worker 在 Pi 基础提示词之后追加 Rally 段落（[03 §1](superagent/03-提示词.md)）。
- 身份、性格、工作方式只影响语气，内置契约不可被覆盖（00 附 A4；原【待定】关闭）。

## 5. 事件与通信改造

### 5.1 事件信封与类型

v3：事件清单见 [01 §7](superagent/01-角色与协议.md)，取代原表。要点：

- 信封 `{seq, ts, taskId?, runId?, sessionId?, type, payload}`；`workerId` 由 `runId` 取代（一个任务可以有多次运行，Q7）。
- **【事实】** Pi 现有核心事件：`agent_start/turn_start/message_start/message_update/message_end/turn_end/agent_end/tool_execution_start|update|end`（`packages/agent/src/types.ts:530-542`）；会话附加事件 `agent_settled{aborted}`、`queue_update{steering,followUp}`（`agent-session.ts:210-251`）。Rally 只包装转发，不改 Pi 原事件。
- 流式增量（`message_update`、`tool_execution_update`）只广播、不落盘（[04 §6](superagent/04-工作区与并发.md)）。

### 5.2 任务状态

v3：改为"事实持久化＋显示状态推导"，推导表见 [01 §3](superagent/01-角色与协议.md)，取代原 worker 状态机。要点：

- 持久化的只有事实：审批、运行（一次运行＝从启动到终态）、汇报、问题、门、终态。
- 显示状态：已取消、完成、无需处理、失败、需处理（待确认／待回答／中断／受阻）、待批准、排队中（`dependency_failed > dependency > write_lock > capacity`）、进行中。
- "需处理"是聚合视图，不是独立状态位。
- 一个任务在等待时不得阻塞队列：scheduler 继续放行其他可运行任务（C5/C6）。

### 5.3 双栏消费同一事件流（【建议默认】）

- 左栏 selector：`sessionId == mainSessionId`，并把 `task_*` 事件渲染成对话内任务卡片（`taskRef`）。
- 右栏 selector：`taskId != null`，按 `taskId` 分组成工位时间线；`access_recorded` 汇成访问痕迹面板。
- 同一 `seq` 流、两个纯函数 selector；重连/重放后 UI 结果可复现（不依赖本地时间戳排序）。

### 5.4 steer / queued 的投递语义（【建议默认】）

- 用户任何时候输入 → 默认进入**主 session**；主 agent 忙时按 Pi `queue_update` 的 `steering`/`followUp` 排队，UI 显示"已排队/已插入"（【事实】Pi 已有 `sendUserMessage(steer/followUp)` 与 `clearQueue`）。
- 要改**运行中任务**：用户只能对主 agent 说，主 agent 调 `task_steer(taskId, quotes, note?)` 下发（原话转发、不改写，Q4）；worker 侧插入点为"当前工具调用结束、下一次模型调用前"（【推断】，待实测，附录 B-3）。已结束的任务用 `task_resume`（Q7）。各种任务状况下的投递方式见 [01 §4.5](superagent/01-角色与协议.md)。
- 右栏整体只读（Q18），避免出现"两个对话上下文"。
- 已关闭（原【待定】）：主 agent **不能**替换 worker 的简报；追加要求只能以新原话的形式送达（Q4 派生 7）。

### 5.5 排队、耗时与只读任务页

- 依赖：任务可声明 `dependsOn`；未满足时 `queued + waiting(dependency)`，UI 文案"排队中 · 等待 X 完成后开始"。
- 名额：并发上限（C6，默认 2）达到时进入 `queued + waiting(capacity)`，UI 文案"排队中 · 等待空闲工位"；两种排队共用状态，文案区分。
- 写锁：同一锁键已有改写任务时进入 `queued + waiting(write_lock)`，文案"排队中 · 等待 T-1045 释放 C:\proj 的写入"（C10）；上游以非完成状态结束时为 `waiting(dependency_failed)`（Q9）。
- 耗时：由 `run_started.at` 计算，renderer 本地每秒刷新；**不产生 tick 事件**，避免事件流膨胀。
- 进度（**D8 已定，v3 修订**）：**不显示百分比，也不显示阶段名**，只显示粗略状态＋时间（Q16）。agent 任务无法可靠估算进度，百分比是假精确；原型的进度条只作风格参考，不实现。用户问"做到哪了"时，主 agent 用 `task_read` 的 `timeline` 视图回答。
- 任务页只读：没有输入框，也没有任务操作按钮（Q18）；"在主对话中提及"按钮把 `taskId` 预填进主对话。

### 5.6 崩溃恢复与重放（【已定】，D3）

- 事件独立 append-only 写 JSONL，带**全局单调 `seq`**；任务快照 `state.json` 定期落盘；**先落盘再广播**。
- 启动时：先载入快照，再重放 `seq > snapshotSeq` 的事件；`running` 任务标记 `interrupted`，以一条中继唤醒主 agent，由用户在主对话里决定续跑或放弃（Q18，[01 §4.9](superagent/01-角色与协议.md)）。
- Pi 会话 JSONL 可继续（【事实】`session-manager.ts:1760-1881`），但**任务状态不能只靠会话重建**。
- **不假设**引入 `packages/durable`；仅借用"检查点＋重放"概念。

### 5.7 访问痕迹（G17，**需求必然**；【建议默认】）

- 每个工具结果投影时提取 `access`。v3 提取规则见 [02 §5](superagent/02-工具规格.md)：新增 `fs_delete`；shell 不解析命令，只记 cwd 与命令文本（不做字符串匹配）。
- 按任务聚合去重，右栏提供"读了什么/改了什么/访问了哪些域"三个清单；这就是"可见性优先于可控性"的落点。

## 6. 门控（分级，按可逆性）

### 6.1 判据与三档（【已定】）

| 档 | 例子 | 行为 |
| --- | --- | --- |
| 可逆 | 改文件、装依赖、跑测试、网络请求、建分支、commit | **不设门** |
| 可逆但有对外代价 | push、发 PR/邮件、部署、调付费 API | **提示，不阻断**（右栏提示条＋审计） |
| 不可逆 | 删数据、drop、强推、覆盖未提交改动、批量清目录 | **停一次，等明确确认** |

### 6.2 门的数量必须极少（【已定】）

门多了用户会条件反射点通过，门就退化成噪声，真信号被稀释。因此：

- 用户侧只有**一个**确认点：派发前审阅（外门，全局开关切换"需要批准/自动批准"，Q17）。
- agent 侧只有**一个**拦截点：不可逆动作（内门）。
- 删除收敛为**单一受控工具** `file_delete`，破坏性 git 操作收敛为受控 `git` 工具；门只守这几个入口（见 6.3）。

### 6.3 不用 shell 字符串匹配（【已定】）

`rm -rf` 有无数变体（PowerShell `Remove-Item -Recurse`、脚本间接删、工具内部删），字符串匹配既漏又误。**【建议默认】**：

1. 新增 `file_delete({ paths, dryRun })`：返回命中数量、实际将删的路径预览、是否含未提交改动；`dryRun` 默认 true。
2. 真正执行必须带一次明确确认（一次性 token 或 `confirm: "DELETE"`），确认后写审计。
3. 系统提示词要求所有删除走该工具；shell 中的删除不在字符串层拦截，只做**可见性**记录（访问痕迹＋审计）。
4. **【待定】** 是否对 shell 删除做"事后告警"（建议：是，记录但不阻断）。
5. v3：破坏性 git 操作（`reset --hard`、丢弃改动、`clean`、强推等）同样收敛到受控 `git` 工具，按参数数组分档，不是 shell 字符串匹配；用户可把 MCP 工具标为不可逆（[02 §3.5、§3.8](superagent/02-工具规格.md)）。本任务输出目录内、或本任务新建文件的删除不过门（02 §3.4）。

**【事实】** 该拦截点可挂 Pi `tool_call` 钩子（`core/extensions/types.ts:1214-1284`，可 `block` 并原地改 `input`）。

### 6.4 外门（用户的）：派发前审阅（【已定】）

- 触发：主 agent 调 `task_dispatch`／`task_resume` → `task_created`（含原话与备注）；全局开关为"需要批准"时进入"待批准"，主对话出现带"批准／取消"按钮的派发卡（[05 §2.2](superagent/05-界面与交互.md)）。
- 开关：沿用原型 composer 的全局开关（`ChatPanel.tsx:199-205`、`Config.autoApprove`），默认"需要批准"（`store.tsx:68`）；**不做按任务覆盖**（Q17，D13）。
- 批准方式：点按钮；或用户说"可以"，由主 agent 调 `task_approve` 引用该消息。不提供编辑表单；修改经主对话由主 agent 调 `task_update`（Q17）。
- 超时：**【建议默认】** 长时间未批 → 保持待批，不自动派发、不拒绝（派发尚未开始，无副作用）。
- 开关只管外门；内门不受开关影响，始终停一次（C5）。

### 6.5 内门（主 agent的）：不可逆动作（【已定】）

- 触发条件收敛为**不可逆清单**（6.1 第三档），不是"任何高危行为"。
- 流程：worker 发起不可逆动作 → 拦截 → 生成 `gate_requested` → 上报主 agent。主 agent **只有在能引用覆盖该动作与范围的用户原话时**才能放行，否则上升用户；拒绝或要求换做法不需要原话（Q24，[01 §4.4](superagent/01-角色与协议.md)）。
- 升级必须携带上下文（【已定】）：具体命令/工具、工作目录、影响范围（路径/行数/对象）、可替代做法。缺任一项则 gate 请求视为无效，返回要求补全（防止主 agent 凭一句话瞎批）。
- worker 在此期间 `waiting(gate)`，工位显示原因；**不阻塞其它任务**。
- 超时＝拒绝（【已定】）：**【建议默认】** 内门 120 秒、上升用户后 10 分钟；超时写 `gate_timeout`，worker 收到拒绝原因并继续/失败，不会永久等待。
- 放行决策记录：`gate_decided{decision, actor: "main"|"user", basis}`，`basis`＝被引用的用户消息 ID 列表。

### 6.6 审计（【已定】）

- 每次**放行**（内门通过、外门手动批准、对外代价动作）写一行：`ts, taskId, workerId, action, actor, basis, result`。v3 补充：主 agent 代答、记忆写入、取消也写一行；文件位置改为 `~/.rally/state/audit.jsonl`（[02 §4](superagent/02-工具规格.md)）。
- 一行 JSON append 到 `audit/audit.jsonl`，右栏可查、可导出；不要求审批流程，只要求可复盘——开源后这是唯一复盘依据。
- **【建议默认】** 明文存储、不做防篡改；日志轮转与脱敏见第 8 节。

### 6.7 与其他机制的关系

| 问题 | 结论 |
| --- | --- |
| 内门与队列 | 不阻塞：一个任务 waiting，scheduler 继续跑其它任务 |
| 内门与主 agent 忙碌 | 超时拒绝，不挂起 |
| 内门与用户 | 仅主 agent 上升时触达用户：主对话里出现确认卡片，不在右栏弹模态 |
| 门控与回滚 | v1 不做回滚（Q21）；内门是不可逆动作的唯一保护 |
