# 定时任务

计划创建时可指定 context:0–30 轮和 memory:0/1，由宿主自动准备聊天与全量记忆背景。每次派发复制创建时的有界快照，不自动重读记忆。具体规则见 [世界感知与任务上下文](世界感知与任务上下文.md)。

2026-11-25 实现。入口是主对话创建或修改，工位 → 定时查看、启停、删除与打开最近任务。

## 支持的表达

| 用户需求 | 保存的时间规则 | 行为 |
| --- | --- | --- |
| 明天下午三点做一次 | `once`，未来毫秒时间戳 | 只派发一次 |
| 从现在开始每两小时 | `interval`，`minutes: 120` | 首次在两小时后；后续保持原节奏 |
| 每天 9 点到 21 点，每两小时 | `interval`＋`window` | 在 9、11、13、15、17、19 点派发；21 点不派发 |
| 周一到周五白天每两小时 | 上一项＋`window.weekdays: [1,2,3,4,5]` | 只在周一至周五的窗口内派发；不识别法定节假日或调休 |
| 每周五 22 点到次日 2 点，每小时 | 跨午夜 `window`＋`weekdays: [5]` | 周五 22、23 点，周六 0、1 点；2 点不派发 |
| 每周一三五上午九点 | `daily`＋`weekdays: [1,3,5]` | 选定星期的当地九点 |
| 周末全天每三小时 | `interval`＋00:00–24:00＋`weekdays: [6,7]` | 每个选定日期从零点计时 |

所有日历时间带 IANA 时区，例如 `Asia/Shanghai`。星期使用 1=周一、7=周日，不填表示每天。时段包含开始、不包含结束；结束早于开始代表跨午夜，星期归属开始日。开始与结束不能相同，全天使用 00:00–24:00。

带时段的间隔从每个窗口的开始时间重新计时，间隔不能超过窗口长度。创建时只选严格晚于当前时间的时刻；例如 10 点创建 9–21 点每两小时的计划，首次为 11 点。用户同时要求“现在先做一次”，主 Agent 再单独派发立即任务。

夏令时跳过不存在的当地时刻，回拨时重复的当地时刻只执行一次。每周指定时刻被夏令时跳过时顺延至下一周。普通无时段间隔按真实经过的分钟数计算。

目前不支持每月、节假日日历、Cron、多段时段或单个计划每天多个任意时刻；不能把这些需求静默近似成已支持的规则。

## 修改与恢复

全局 [闲置保护](闲置保护.md) 默认在连续 72 小时未发言后暂停派发及执行，直到下一条用户消息。它不修改计划的启停状态；以下运行时段与合并规则在恢复后继续适用。

- `schedule_update` 可原地替换完整 `timing`，保留计划 ID、工作内容与历史任务。主 Agent 必须先查看计划，保留用户仍要求的限制，并引用修改时间的原话。后续 Worker 同时保留原始工作要求和修改依据。
- 时间发生变化、或停用转启用时，从当前时间重新选未来时刻。重复启用或重复提交等价时间规则不会改变下次时间。只改时间不会自动启用已暂停的计划。过期单次任务可以改为未来时间后重新启用。
- Rally 关闭或休眠期间不会执行。恢复后只合并补一次，不逐条补齐。恢复时不在允许星期或时段内，则跳过积压，等待下一个有效时刻。排队中的已派发任务保留自身的时间规则，首次启动同样受限。
- 同一计划上一轮未结束时，不派发下一轮。等待批准、等待回答、等待权限、排队和重启中断都算未结束；定时页和 `schedule_list.waitingFor` 显示原因。重启中断的 Worker 需要继续或取消，宿主不会自动重做可能已经发送过的邮件等动作。
- 运行时段限制新一轮的首次启动。已经启动的任务继续收尾，用户显式继续中断任务也不重新套用首次启动限制。
- 暂停、删除或改时间不取消、不改写已经派发的 Worker；它保留派发时的时间规则。取消 Worker 不删除计划。“停止计划和当前任务”需要分别处理两者。
- 每次派发沿用当时的批准模式、模型及工具权限。计划创建成功仅表示保存成功，不表示工作已完成。

派发使用计划 ID 与本次应执行时间组成持久化键。若在创建 Worker 后、保存计划进度前重启，会找回同一 Worker，不重复创建。旧计划和旧任务无需迁移；没有新字段时沿用原来的单次、间隔或每日行为。
