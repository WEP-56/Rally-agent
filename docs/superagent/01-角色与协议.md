## 0. 四条原则

1. **原话至上**（Q4/Q8/Q23/Q24）：需求、代答、放行、记忆，唯一依据是用户在主对话里说过的话。主 agent 只能**引用**，不能改写；凡是改变任务或替用户做决定的工具，都要带原话引用，由工具层校验。
2. **主 agent 只读、只调度**（Q1）：它能看、能派、能转达，不能改项目里的任何东西。
3. **打扰最少**（Q3，dsh `000-philosophy`）：只有当用户能用上结果、或必须由用户行动时才发言。
4. **可见性优先于可控性**（C5）：门极少；做了什么由系统记录、展示，而不是事先层层审批。

## 1. 角色

| 角色 | 是什么 | 持有 | 不做 |
| --- | --- | --- | --- |
| 用户 | 唯一的需求来源和决定者 | 主对话输入框、主对话里的卡片按钮 | 不直接和任务 agent 对话（Q18：右栏只读） |
| 主 agent | 一个永续的 Pi `AgentSession`（Q11） | 只读工具＋任务工具＋记忆工具（Q1/Q23） | 不写项目文件、不跑命令、不替任务做技术决定、不凭自己判断替用户拍板 |
| 任务 agent（worker） | 每个任务一个 Pi `AgentSession`（D2），只有这一种类型（Q13） | 编码工具＋作业/服务＋联网/GitHub/MCP＋汇报（Q19） | 不能开子 agent（Q15），不能直接找用户，不读记忆 |
| 系统（Supervisor） | Electron 主进程里的确定性部分 | 任务存储、调度、写范围信号、中继、门控、审计 | 不调用模型做决定；只执行规则；不做写锁 |

谁决定什么：

| 事项 | 决定者 | 依据 |
| --- | --- | --- |
| 要做什么 | 用户 | 原话 |
| 派给谁、拆不拆、依赖关系、改写还是只读 | 主 agent | 原话＋只读侦察 |
| 怎么做（技术路线） | 任务 agent | 原话＋项目上下文 |
| 做完没有 | 任务 agent（Q10：说完成就完成） | 自己的判断；系统补齐证据 |
| 回答任务 agent 的问题 | 主 agent（有原话依据时）否则用户（Q8） | 原话 |
| 放行不可逆动作 | 主 agent（有原话依据时）否则用户（Q24） | 原话 |
| 派发前批准 | 用户或自动（Q17 全局开关） | — |
| 停止、续接、重试 | 用户，经主 agent 执行（Q18） | 原话 |

## 2. 领域对象

### 2.1 消息与原话

- 主对话的每条消息都有**全局唯一、永久有效**的 ID，形如 `#1203`（全局递增，短，方便模型抄写）。ID 跨压缩、跨物理分段都有效（Q11、附 A10）。
- 模型上下文里，用户消息带 ID 前缀（`[#1203] …`），界面上不显示前缀。
- **原话**＝`role=user` 的消息。系统事件（中继、通知）虽然也以 user 角色进入模型上下文，但带 `<rally-event>` 包裹且没有 ID，**不能被引用**。
- **已确认的提议**：当用户消息只是确认主 agent 的提议（"就按方案 B"）时，引用可以带 `withProposal: true`，系统会把该用户消息之前紧邻的那条主 agent 消息一并附上，并标注"主 agent 提议 · 用户已确认"（Q4 派生 3）。主 agent 消息不需要自己的 ID。
- 引用在写入任务时**冻结**为副本（文本＋附件＋时间），之后与对话脱钩。

```ts
interface Quote {
  messageId: string;          // "#1203"
  kind: "user" | "proposal";  // proposal 只能由 withProposal 带入
  text: string;
  at: number;
  attachments?: { path: string; mime: string }[];
}
```

### 2.2 任务、运行、输入

参照 dsh 的 `Ticket`/`Assignment`/`TicketInput`，删去来源、授权、订阅等桌面端用不上的概念。

```ts
type TaskMode = "write" | "readonly";                                  // Q6
type ReportState = "progress" | "ready" | "blocked" | "failed" | "dropped";
type TaskOutcome = "done" | "failed" | "dropped" | "cancelled";
type QueueReason = "dependency_failed" | "dependency" | "capacity";   // write_lock 已删除（04 §2）

interface Task {
  id: string;                  // "T-1045"（附 A7）
  title: string;               // ≤40 字符
  quotes: Quote[];             // ≥1，派发时冻结
  note?: string;               // ≤30 词（中文按 Intl.Segmenter 分词计）
  cwd: string;                 // 规范化绝对路径（04 §2.4）
  scope: string[];             // 预计写入的路径范围（04 §2.2；只警告，不排队）
  mode: TaskMode;
  outputDir: string;           // <默认工作区>/outputs/<id>-<slug>/（Q6 派生 1）
  dependsOn: string[];
  createdAt: number;
  approval: { state: "pending" | "approved" | "cancelled"; by?: "auto" | "button" | "main"; basis?: string[]; at?: number };
  runs: Run[];
  inputs: TaskInput[];
  attention?: Attention;       // 同时最多一个（Q8 派生 1）
  attentionHistory?: Attention[]; // 已答/替换/撤回/失效记录；主对话保留，不受右栏 20 条窗口限制
  gate?: Gate;                 // 同时最多一个
  ended?: { at: number; outcome: TaskOutcome; by: "worker" | "main" | "system"; reason?: string };
  usage: { inputTokens: number; outputTokens: number; costUsd?: number; toolCalls: number };  // Q12 可见性
  changedFiles?: string[];     // 进入终态时由访问痕迹汇总（04 §2.2）
}

interface Run {                // 对应 dsh Assignment：一次从启动到终态的执行
  id: string;
  n: number;                   // 第 N 次运行（Q7）
  trigger: "dispatch" | "resume" | "recovery";
  model: string;               // 启动时的任务 agent 模型（Q22）
  startedAt: number;
  endedAt?: number;
  endReason?: "ready" | "failed" | "dropped" | "cancelled" | "interrupted" | "stalled";
  lastReport?: { state: ReportState; summary: string; at: number };
}

interface TaskInput {          // 首条消息之后送达 worker 的一切
  id: string;
  kind: "steer" | "answer" | "resume" | "upstream" | "job_done" | "gate_result" | "nudge";
  quotes?: Quote[];
  note?: string;
  body?: string;               // 系统生成的正文（作业结果、门控结果等）
  questionId?: string;         // answer 关联的原问题
  at: number;
  deliveredAt?: number;        // 已交给 Pi 会话
  readAt?: number;             // 已被某一步取入历史（崩溃恢复判断是否重投）
}

interface Attention { id: string; question: string; options?: string[]; runId: string; askedAt: number;
  escalatedAt?: number; answer?: { by: "main" | "user"; basis: string[]; text: string; at: number };
  closed?: { reason: "replaced" | "cleared" | "task_ended" | "run_ended"; at: number } }

interface Gate { id: string; tool: string; action: string; cwd: string; scope: string[]; alternatives: string;
  requestedAt: number; escalatedAt?: number;
  decision?: { value: "allow" | "deny" | "timeout"; actor: "main" | "user" | "system"; basis?: string[]; reason?: string; at: number } }
```

要点：

- 任务定义自己的状态，**不跟随** Pi 会话的忙闲（dsh `001-domain` 被否决的概念："Ticket state that follows the DSH Session"）。
- 一个任务可以有多次运行：首次派发、续接（Q7）、崩溃恢复。同一任务的所有运行共用同一个 Pi 会话文件（`sessions/tasks/<id>.jsonl`），上下文连续。
- `blocked` 不结束运行；用户答复后同一次运行继续。只有终态与中断才结束运行。

### 2.3 汇报

worker 改变任务状态的**唯一**入口是 `task_report`（02 §3.9）。

| state | 含义 | 任务效果 | 唤醒主 agent |
| --- | --- | --- | --- |
| `progress` | 继续干，可选带问题 | 无（只记入时间线） | 仅当带问题时 |
| `ready` | 原话要的结果已完成 | 终态 `done`（Q10：没有待验收） | 是 |
| `blocked` | 没有用户介入就无法继续 | 保持打开、空闲（释放名额；`scope` 不占用） | 是 |
| `failed` | 做不成，且不是缺用户输入 | 终态 `failed`，可续接 | 是 |
| `dropped` | 无事可做（不复现、已被别处解决） | 终态 `dropped`，可续接 | 是 |

- **忘记汇报**：worker 结束一轮、没有作业在跑、也没调 `task_report` 时，系统追加一条提醒（`nudge`）让它汇报。再次空手结束 → 系统记为 `blocked`，摘要取它最后一段文字，并唤醒主 agent。
- 终态之后，该任务的一切 worker 工具调用都被拒绝（dsh："Tool calls are refused after the Ticket ends"）。

## 3. 任务显示状态

持久化的只有事实（审批、运行、汇报、问题、门、终态）。界面上的"粗略状态"（Q16）由下表**推导**：自上而下，首个命中为准（同 dsh `ticketStage`）。

| 显示 | 条件 | 文案示例 |
| --- | --- | --- |
| 已取消 | `ended.outcome = cancelled` | 已取消 |
| 完成 | `ended.outcome = done` | 已完成 · 13:05 |
| 无需处理 | `ended.outcome = dropped` | 无需处理 |
| 失败 | `ended.outcome = failed` | 失败 |
| 需处理 · 待确认 | 有未决门且已上升给用户 | 等你确认：删除 12 个文件 |
| 需处理 · 待回答 | 有未决问题且已上升给用户 | 等你回答 |
| 需处理 · 中断 | 最近一次运行 `endReason = interrupted`，且之后没有新运行 | 因 Rally 重启中断 |
| 需处理 · 受阻 | 最近汇报 `blocked`，且之后没有新输入 | 受阻 |
| 待批准 | `approval.state = pending` | 待批准 |
| 排队中 | 未启动；原因按 `dependency_failed > dependency > capacity` 取第一个 | 排队中 · 等待空闲工位 |
| 进行中 | 其余（含后台作业运行中、问题或门正由主 agent 处理） | 进行中 · 4 分钟 |

"需处理"是聚合视图，不是独立状态位（沿用改造计划 5.2）。

## 4. 主流程

### 4.1 派发

1. 用户发消息 → 主 agent 用只读工具了解情况（可选）→ 调 `task_dispatch`。
2. 系统校验：引用存在且是用户消息；cwd 是 router 明确指定的、存在的绝对目录；依赖存在且无环；标题与备注长度；`scope` 规范化。不通过 → 工具报错，主 agent 修正。`scope` 与运行中任务交叉 → 不报错，返回警告并在事件流记 `task_scope_overlap`（04 §2.2）。
3. 写入 `task_created`。全局开关为"自动批准" → 立即 `approval=approved(by: auto)`；否则 `pending`，主对话显示带"批准／取消"按钮的派发卡（Q17）。
4. 批准方式：用户点按钮（系统直接处理，并给主 agent 一条不唤醒的通知）；或用户说"可以"，主 agent 调 `task_approve` 引用这条消息。
5. 批准后进入调度（04 §3）：依赖全部完成、有空闲名额 → 启动运行：建 Pi 会话，发送首条消息（[03-提示词 §5.1](03-提示词.md)）。写范围交叉不阻止启动（04 §2）。
6. 主 agent 的回执（4.1 契约）：taskId、标题、一句话说明要做什么、依赖。不含验收标准（Q4）。

### 4.2 汇报与唤醒（Q3）

1. worker 调 `task_report` → 系统落盘 → 若在唤醒集合内（见下），把一条**中继**放入主 agent 的中继队列。
2. 中继队列有序、至少一次投递、按 `relayId` 幂等（dsh `relay` effect）。
   - 当前实现：事件流保存正文、源事件序号与 relayId；派生入队未完成可从源事件重建。送入 Pi 队列还不算 delivered，首次进入模型上下文时才确认，正文/系统行按 ID 去重；Pi 历史已保存而确认缺失时只追加恢复指针。失败退避重试，未选择主模型时保留待发。这里保证上下文投递，不保证供应商成功回复或任意模型动作 exactly-once。
   - 首次启用以 `relay_started` 标定边界；旧版仅记录 ID、缺少载荷与真实消费确认的历史不追溯补发。失效问题/内门记 relay_discarded；停止主会话后未读队列保留至下一轮或重启。
3. 主 agent **空闲**：等待约 2 秒，收集窗口内的其他中继，合并成一条系统消息，**发起新的一轮**。主对话先出现系统行（"T-1045 已完成"），再接主 agent 的发言。
4. 主 agent **忙**：中继以 steer 方式并入当前轮，在当前工具调用结束、下一次模型调用之前注入（Pi `steer` 语义，见 §8）。
5. 主 agent 被唤醒后可以不发言（例如该说的已经说过），空结束即可。

唤醒集合：`ready`、`blocked`、`failed`、`dropped`、带问题的汇报、内门请求、上游失败（`dependency_failed`）、启动时的中断清单、卡死判定失败。

**不唤醒，只作为通知**（主 agent 下一轮自然看到）：任务开始运行、用户点按钮批准/回答/确认、作业与服务事件（只发给 worker）、外部代价动作提示。

### 4.3 提问与代答（Q8）

1. worker：`task_report({ state: "progress" | "blocked", summary, question, options? })` → 系统开 `attention`（同一任务的新问题覆盖旧问题，同一问题重复提交只算一次）。
2. 中继 `worker_question` 唤醒主 agent，主 agent 二选一：
   - **代答**：`task_answer(taskId, questionId, quotes, note?)`，`quotes` 至少 1 条且必须是用户原话，工具层校验。worker 收到"用户此前说过：〈原话〉（主 agent 备注：…）"。
   - **转给用户**：`escalate({ kind: "question", taskId, id })` → 主对话出现需处理卡片，问题文本**逐字复制** worker 原文，带选项按钮。
3. 用户点选项 → 系统直接回传 worker，并通知主 agent（不唤醒）。用户打字回答 → 主 agent 调 `task_answer` 引用这条新消息。
4. **兜底**：主 agent 被唤醒的这一轮结束时，若问题既没被回答也没被转出，系统自动转给用户。
5. 投递：worker 正在一轮中 → steer；worker 空闲（`blocked`）→ 唤醒它（需要名额，优先于新任务，04 §3.2）。

### 4.4 内门：不可逆动作（C5，Q24）

1. worker 调用受控工具的不可逆形态（`file_delete` 非 dry-run、`git` 破坏性子命令、被标为不可逆的 MCP 工具）→ Pi `tool_call` 钩子拦截，系统建 `gate`。请求必须带动作、工具、cwd、影响范围、可替代做法，缺项直接拒绝并要求补全。
2. 该工具调用**挂起等待**决定（worker 这一轮阻塞在这个调用上；不可逆动作很少，v1 接受占用名额）。
3. 中继 `gate_request` 唤醒主 agent：
   - **放行**：`gate_decide(gateId, "allow", quotes, reason)`，引用的原话必须覆盖这个动作和范围。
   - **拒绝**：`gate_decide(gateId, "deny", reason)`，可以不带原话。
   - **上升**：`escalate({ kind: "gate", taskId, id })` → 主对话出现确认卡片，逐字展示请求与影响范围，带"允许／拒绝"按钮。
4. 超时＝拒绝：主 agent 120 秒；上升给用户后 10 分钟（改造计划 6.5）。被挂起的工具调用返回拒绝原因，worker 换做法或汇报 `blocked`。
5. 放行后由系统按**被批准的参数原样执行**，结果作为工具返回值交给 worker。
6. 每次决定写一行审计：`ts, taskId, gateId, action, scope, decision, actor, basis`。
7. 兜底同 4.3 第 4 条：主 agent 一轮结束仍未决定 → 自动上升给用户。

### 4.5 插话：给运行中的任务追加要求

`task_steer(taskId, quotes, note?)`，原则同派发（Q4 派生 7）。

| 任务状况 | 处理 |
| --- | --- |
| 未启动（待批准/排队中） | 追加到该任务的原话，随首条消息一起送达 |
| 运行中（worker 正在一轮中） | Pi steer：当前工具调用结束后注入 |
| 打开但空闲（`blocked`） | 唤醒 worker（需要名额，优先） |
| 已结束 | 拒绝，提示改用 `task_resume` |

### 4.6 续接（Q7）

- `task_resume(taskId, quotes, note?, mode?)`，适用于已结束的任务和"中断"的任务。
- 新建一次运行（`trigger=resume`，n+1），重新排队：要名额；补填 `scope`（改写时）；审批规则与派发相同（Q17），依赖不再检查。
- 续接消息：原话＋备注＋"这是第 N 次运行"。来自中断的续接，额外附**恢复提示**（[03 §5.6](03-提示词.md)）：先检查目录与 git 状态，再决定是否重复任何对外动作（dsh 003 Restart）。
- 主 agent 的选择规则：同一目标或同一批文件 → 续接；新目标 → 新建任务。原会话已接近压缩阈值时，倾向新建任务，并以原任务为上游依赖（Q7 派生 6）。

### 4.7 取消

- `task_cancel(taskId, quotes)`：只在用户要求时调用（Q18 全部经主对话）。
- 未启动：直接结束为 `cancelled`。运行中：Pi `abort` 当前轮 → 最多等 10 秒 → 杀掉该任务的作业进程树 → 结束为 `cancelled`；释放名额；服务保留（Q14 派生 6）。
- 下游任务因此进入 `dependency_failed`，信息附在 `task_cancel` 的返回值里，不再另发中继唤醒。

### 4.8 依赖（Q9）

1. B 声明 `dependsOn: [A]`。A 完成前，B 处于 `queued(dependency)`。
2. A 完成 → B 可启动。B 的首条消息附上每个上游的任务卡、汇报摘要（≤600 字）、产出目录、改动文件清单（来自访问痕迹）。B 可以用 `task_read` 读上游的完整汇报，但**只能读自己的上游**。
3. A 以非完成状态结束（失败/取消/无需处理）→ B 进入 `queued(dependency_failed)` → 唤醒主 agent。
4. 主 agent 处理时同样遵守原话规则：取消 B、改 B 的依赖、续接 A，都要用户的话作依据。所以通常是主 agent 告诉用户"A 失败了，原因…，要重试 A，还是让 B 单独做／取消？"，再按用户的回答调工具。

### 4.9 崩溃恢复（D3）

1. 启动：单实例锁 → 载入快照 → 重放 `seq > snapshotSeq` 的事件 → 正在进行的运行记为 `interrupted`（工具调用中途被打断的，结果记为"未知"，改造计划第 8 节）。
2. 待批准、排队中、`blocked` 的任务原样保留；调度器照常运行。
3. 把中断清单作为**一条**中继唤醒主 agent；主 agent 向用户汇报并询问续跑或放弃。续跑＝`task_resume`（引用用户的回答），放弃＝`task_cancel`。这样保留了 D3"提供续跑/放弃"的语义，入口在主对话（Q18）。
4. 送达但未被取入历史（`readAt` 为空）的输入，在新运行的首条消息之前重投；仍留在 Pi 会话里的副本先移除，保证只有一份（dsh 003 Restart）。

## 5. 中继与通知格式（模型可见）

中继以 user 角色进入主 agent 上下文，用 `<rally-event>` 包裹，不带消息 ID，**不是原话**。界面上渲染为系统行或卡片，不是用户气泡。

```text
<rally-event kind="worker_report" task="T-1045" state="ready">
title: landing 页响应式适配 · write · C:\proj
summary: 三个断点已适配，导航栏小屏改为汉堡菜单；npm run build 通过，未跑视觉回归。
changed: src/landing.css, src/components/Nav.tsx (+2)
outputs: C:\Users\me\rally\outputs\T-1045-landing\
more: task_read T-1045 report
</rally-event>

<rally-event kind="worker_question" task="T-1046" question="Q-12">
question: 旧的 /api/v1/price 还有调用方吗？保留兼容层还是直接删？
options: 保留兼容层 | 直接删除
</rally-event>

<rally-event kind="gate_request" task="T-1047" gate="G-3" timeout="120s">
action: file_delete · cwd C:\proj
scope: dist/ (412 files), coverage/ (37 files)
alternatives: 只删 dist/
</rally-event>

<rally-event kind="dependency_failed" task="T-1049" upstream="T-1048" upstream_outcome="failed">
upstream summary: 无法访问 github.com（超时 3 次）
</rally-event>

<rally-event kind="interrupted" tasks="T-1050,T-1051">
Rally 重启时这些任务正在运行。
</rally-event>

<rally-notice>用户点按钮批准了 T-1045。</rally-notice>
```

- 摘要超过 600 字时截断，并给出 `task_read` 指针（dsh `resultRelay`）。
- 合并唤醒时，多个 `<rally-event>` 放在同一条系统消息里，按入队顺序排列。
- `<rally-notice>` 不发起新的一轮，跟随下一轮的上下文进入。

## 6. 主 agent 的上下文（Q11 永续单对话）

### 6.1 构成

| 部分 | 内容 | 变化频率 | 位置 |
| --- | --- | --- | --- |
| 静态系统提示词 | 共享规则、主 agent 角色、人设（附 A4） | 只在设置改变时 | system prompt（利于缓存） |
| 对话历史 | 用户消息（带 `[#id]`）、主 agent 发言与只读工具调用、中继、通知 | 每轮追加 | Pi 会话 |
| 压缩摘要 | Pi 压缩产物 | 每次压缩 | Pi 会话 |
| **Rally 状态块** | 时间、主对话默认工作区与只读最近项目、打开的任务清单、等待处理的问题/门、记忆（Q23） | 每轮重建 | 每次模型调用前临时注入，**不落盘** |

状态块示例：

```text
<rally-state time="2026-11-08 14:02" project="C:\proj (git main)">
tasks:
- T-1045 进行中 4m · write · C:\proj · landing 页响应式适配
- T-1046 排队中(等待空闲工位) · write · C:\proj · 导航栏汉堡菜单
- T-1044 需处理·待回答(Q-12) · readonly · ~/rally · 抓取竞品定价
waiting on you: Q-12(T-1044)
memory:
- 回复用中文，结论先行
- C:\proj 用 pnpm，不要用 npm
</rally-state>
```

### 6.2 压缩

- 压缩只影响模型上下文；界面始终显示完整历史，压缩点显示为分隔条"上文已整理"（Q11 派生 1）。
- 不依赖摘要保存的东西：任务清单、未决问题、主对话默认工作区、记忆。它们每轮都由状态块重新注入（dsh：压缩后核对工单，避免重复派发）。
- 压缩提示词要求保留：用户的长期偏好与约束、尚未完成的讨论、做过的承诺；摘要里提到的消息保留 `#id`。
- "整理上下文"按钮＝手动触发一次压缩（Q11 派生 5）。
- 压缩之后需要更早的原话时，主 agent 用 `chat_search` 检索完整历史，拿到 `#id` 再引用。

### 6.3 物理分段

主会话文件超过阈值（建议 20MB，或累计 N 次压缩）时，新开一个物理会话文件：以最近一次压缩摘要和近期消息为起点，并指向上一段。消息 ID 跨段有效，界面历史跨段拼接（Q11 派生 4）。
