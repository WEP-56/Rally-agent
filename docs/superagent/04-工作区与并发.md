## 1. 目录模型

四类目录，各管各的：

| 目录 | 是什么 | 谁写 | 来源 |
| --- | --- | --- | --- |
| 任务工作目录 | router 为每个 worker 明确指定的绝对 cwd；最近项目只记录实际运行历史，不可选择 | 改写任务 | Q5，2026-11-09 修订 |
| 主对话默认工作区 | `~/rally`，只在设置 → 项目与工作区修改；主 agent 相对读取以此为基准；保留 `notes/ reports/ repo/` | 任务 | Q5 |
| 任务产出目录 | `<默认工作区>/outputs/<taskId>-<slug>/`，每个任务一个，用户可直接浏览 | 该任务 | Q6 |
| Rally 状态目录 | `~/.rally/`：会话、事件、审计、记忆、作业日志 | 只有系统 | C4 |

```text
~/.rally/                              # 与 ~/.pi 并存（C4）
├─ workspace.json                      # 主对话默认工作区、只读最近任务项目；无当前项目选择
├─ agent/                              # Pi agent 目录（piConfig 改名后，改造计划 7.2）
│  ├─ settings.json  models.json  auth.json  mcp.json
│  ├─ skills/  extensions/  prompts/  themes/
│  └─ sessions/
│     ├─ main/0001-<ts>.jsonl …        # 主会话物理分段（Q11）
│     └─ tasks/T-1045.jsonl …          # 每个任务一个会话文件（Q5 派生 7）
├─ state/
│  ├─ events-0001.jsonl …              # 全局 seq 事件流，按大小分段（D3）
│  ├─ snapshot.json                    # TaskStore 快照
│  ├─ writer-lock.sqlite               # 进程生命周期 OS 锁，不存业务数据
│  ├─ audit.jsonl                      # 审计，只追加
│  ├─ processes.json                   # Git/作业/服务/MCP/搜索宿主的 PID 与创建时间（§7）
│  └─ jobs/J-3.log  S-2.log …          # 作业与服务的输出
└─ memory/MEMORY.md                    # 记忆（Q23）

~/rally/                               # 默认工作区（Q5）
├─ notes/  reports/  repo/
└─ outputs/T-1045-landing/ …           # 任务产出目录（Q6）
```

日志沿用改造计划 7.2：`%LOCALAPPDATA%\Rally\logs`。Electron 自身数据（窗口状态、浏览器缓存）放在 `%APPDATA%\Rally`。

- 主会话的 cwd 固定为 `~/.rally/agent/main/`，不随默认工作区修改；主只读工具的相对路径按默认工作区解析（Q5 派生 2）。顶部栏不增加工作区入口，保留拖拽区域。
- 修改默认工作区只影响之后的主相对读取和新建任务产出位置，不迁移已有任务目录。最近项目最多 10 个，仅展示 worker 实际启动的 cwd，不参与路由选择。
- worker 的 cwd＝任务 cwd；Pi 按它加载 `AGENTS.md` 与项目内 `.rally/`（项目内扩展需先信任项目，附 A3）。

## 2. 写范围：声明 + 重叠警告（已定，2026-11-08，推翻原写锁方案）

### 2.1 结论：不做锁

- 宿主**不实现任何锁、租约或目录归属**，也没有阻塞式 `acquire`。
- 并发单元只有"名额"（§3.2）；写范围仅作为任务事实记录，宿主不当门。
- 理由：单人桌面、并发默认 2，锁的维护成本（路径规范化、git 工作树根判定、持锁区间、锁泄漏、用户的 IDE 手改）高于收益；静默覆盖风险改由三条轻量信号兜底：
  1. 派发时的 `scope` 交叉**警告**（§2.2）；
  2. 任务结束时记录**实际改动过的文件**（§2.2）；
  3. `write/edit` 的"读后被改"检测（§2.5）。
- 真要并行同一仓库时，正确做法是用户自己开 `git worktree`，而不是让宿主切细锁。

### 2.2 `scope` 声明与重叠警告

- 主 agent 派发时填 `scope: string[]`：本任务预计写入的路径范围（绝对路径或相对任务 cwd）；宿主按 §2.4 规范化后存进 `Task.scope`。
- 派发时若 `scope` 与**运行中任务**的 `scope` 路径段前缀有交叉：
  - **不阻止派发**，任务照常创建（待批准或自动批准）；
  - 工具返回一条 `warnings` 文案（例如"T-1045 正在写 C:\proj\web，与本任务重叠"）；
  - 事件流记 `task_scope_overlap{taskId, withTaskId, paths}`。
- 主 agent 的系统提示词（03 §1.1）加入纪律：派发前先看运行中任务的写范围；重叠时要么串行，要么明确告知用户"这两个任务会并行写同一片区域"；用户坚持就照派，警告仍然记录。
- 任务进入终态时，把本次运行实际改动过的文件写进 `Task.changedFiles`（复用 G17 访问痕迹：`write/edit` 的目标路径，`bash/powershell` 能识别的重定向目标；shell 的间接改动无法覆盖，见 §2.5）。
- 只读任务同样填 `scope`（通常为空）——它不能写项目目录，只能写产出目录（Q6）。

### 2.3 构建产物隔离（提示词兜不住的一类）

- `out/`、`dist/`、`node_modules/`、`.vite/` 等共享输出不能只靠纪律：两个任务并行跑构建会互相覆盖，且宿主无法可靠判断哪条命令会写这些目录。
- 规则：每个任务的构建输出必须带任务独立后缀（如 `--outDir dist-T-1045`，或设置 `RALLY_TASK_ID=T-1045` 让构建脚本自行加后缀）；无法加后缀的构建步骤必须串行（在一个任务里跑完，或由主 agent 明确安排先后）。
- 这条写进主 agent 与 worker 的提示词；任务结束时实际输出目录进 `changedFiles`，事后可追。

### 2.4 Windows 路径规范化

用于只读检查、`scope` 比较、访问痕迹，规则统一：

1. `path.resolve` 得到绝对路径；`/` 统一为 `\`；盘符大写；去掉末尾 `\`（根目录除外）。
2. 用 `fs.realpathSync.native` 解析 junction 与符号链接，防止通过链接绕过只读检查或让 scope 比较失真。
3. 比较时大小写不敏感（键统一转小写存储）。
4. 去掉 `\\?\` 前缀再比较；UNC（`\\server\share`）、`\\wsl$\` 按普通路径处理。
5. 路径超过 240 字符时，实际文件操作加 `\\?\` 前缀（改造计划 7.3）。

### 2.5 兜底

没有锁，写入冲突由以下事实暴露，而不是阻断：

- `write/edit` 的"读后被改"检测（02 §3.1）：文件在本 session 读取后被他人修改则拒绝写入、要求重读。
- 当前实现把读取版本保存在任务 JSONL，重启/续接仍检查；成功自身写入更新版本。此检查不监视 shell 内部操作，不提供外部程序与写盘之间的原子互斥；没有新增宿主文件锁。
- `task_scope_overlap` 警告与 `changedFiles` 记录：事后可追，界面可提示"两个任务都改了 X"。
- 只读任务通过 shell 写了项目目录的，访问痕迹不一定能看到——作为已知局限记入文档（D15：记录不阻断）。

## 3. 调度

### 3.1 放行条件

一个任务可以启动运行，当且仅当：

1. `approval = approved`；
2. `dependsOn` 中的任务全部为 `done`（首次运行；续接不再检查）；
3. 有可用名额（§3.2）。

`scope` 交叉**不是**放行条件，只在派发时给出警告（§2.2）。

队列按"类别优先级 → 进入队列的时间"排序。**排在前面但不能放行的任务不挡后面的任务**（没有队头阻塞，改造计划 5.2）。

### 3.2 名额（C6）

- 上限默认 **2**（设置可调）。
- 占名额：worker 正在一轮中（含挂起在门上的调用），或有后台作业在跑（Q14 派生 3）。
- 不占名额：待批准、排队中、`blocked` 且空闲、中断、终态。
- 优先级（参照 dsh `WorkerSlots`）：

| 类别 | 例子 | 优先级 | 可用额外名额 |
| --- | --- | --- | --- |
| 用户发起的唤醒 | 回答问题、追加要求（唤醒空闲 worker）、续接 | 最高 | ✓ 可以超出上限 1 个 |
| 系统唤醒 | 作业结束唤醒空闲 worker | 中 | ✗ |
| 新运行 | 首次派发 | 普通 | ✗ |

  额外名额的作用：新派发的任务占满名额时，用户仍能立刻继续一个已有任务（dsh："New work therefore cannot prevent a person from continuing an existing Ticket"）。【建议默认】

实施（2026-11-10）：Scheduler 统一接纳新运行与空闲 worker 输入，按上述类别、对应待送输入时间排序；首次派发按批准时间排序。用户续接/回答/追加最多使全局占位达到 `limit + 1`，首次运行前的追加不变成用户续接。流式会话、后台作业和异步启动预留按任务去重；已由作业占位的任务唤醒不再扣名额。结束的启动不继续占位；旧启动晚返回不会删除新运行的预留。依赖失败/等待规则不变。

### 3.3 排队原因与文案

| 原因 | 文案 |
| --- | --- |
| `dependency_failed` | 排队中 · 上游 T-1042 失败，等待处理 |
| `dependency` | 排队中 · 等待 T-1042 完成后开始 |
| `capacity` | 排队中 · 等待空闲工位 |

多个原因同时成立时按上表顺序取第一个（01 §3）。原 `write_lock` 原因随"不做锁"一并删除（§2）。

### 3.4 成本说明（沿用改造计划 2）

每路并行 worker 都是一份独立上下文和一路 API 请求；上限调高会线性增加 token 消耗与限流风险。设置页注明"每增加 1 路，约增加一份上下文成本"。

## 4. worker 会话生命周期

| 阶段 | 做什么 |
| --- | --- |
| 创建（首次运行） | 用 Pi SDK 在主进程内创建 `AgentSession`：cwd＝任务 cwd；模型与思考强度＝"任务 agent 模型"设置（Q22）；工具＝02 §3；系统提示词＝03 §1.2；会话文件＝`sessions/tasks/<id>.jsonl`；挂上 Rally worker 扩展（`tool_call` 钩子、汇报工具） |
| 首条消息 | 03 §5.1（原话＋备注＋上游结果） |
| 运行中 | 订阅会话事件 → 转成 Rally 事件（带 `taskId/runId`）→ 先落盘再广播 |
| 空闲 | 一轮结束且没有作业：`blocked`／等回答时释放名额，会话对象保留在内存 |
| 终态 | 取消订阅，释放 `AgentSession`（D2"完成即归档"），JSONL 保留 |
| 续接 | 用同一 JSONL 重新打开会话，模型取当前设置（Q22 派生 2，待 Pi 实测），发续接消息（03 §5.5） |

### 4.1 卡死检测（Q12）

- 每个占名额的运行都有看门狗，记录最后一个事件的时间。
- 10 分钟没有任何事件、且没有后台作业在跑 → `abort` 当前轮，发送卡死重试提醒（03 §5.9），这次不计失败。
- 重试后又 10 分钟无事件 → 运行结束（`endReason=stalled`），任务 `failed`，唤醒主 agent。
- 没有预算上限（Q12）；用量实时显示（`usage_updated`）。

实施（2026-11-10）：每秒使用单调时钟检查，所有 Pi 会话事件及前台 shell 输出刷新最后活动时间；初始化也纳入检测。仅已转后台且仍运行的作业暂停计时，最后一个后台作业结束后重新给满 10 分钟；服务不豁免 worker，空闲/待批准/排队不误判。首次超时先持久记录 `run_stall_retry` 与该运行的 `stallRetries=1`，等待 abort 真正结束后用同一会话、运行和原模型发送 §5.9 提醒及待送输入。显式续接创建新运行，重新获得一次重试机会。

重试后再超时由系统写失败报告，`endReason=stalled`，沿持久中继唤醒主 agent。若首次 abort 或初始化始终不返回，另等 10 分钟后仍判失败，释放名额、拒绝晚到结果，不启动重叠请求。取消/退出期间不再重试。此处保证任务终态与不重叠；无法终止的第三方初始化/会话仍可能阻塞资源关闭，应用退出守卫见 §7，运行期间的任意挂死仍未全部解决。MCP stdio 与 grep/find 的受管进程覆盖见 §5.4。

### 4.2 模型调用失败（附 A8）

网络错误与 HTTP 408/429/5xx：按 2s、4s、8s 退避自动重试 3 次（Pi 若已有自动重试则沿用，不重复叠加）。仍失败 → 任务 `failed`，唤醒主 agent。

## 5. 后台作业与服务（Q14）

### 5.1 作业

1. `bash`/`powershell` 启动子进程，输出同时写入 `state/jobs/<jobId>.log` 和内存环形缓冲。
2. 30 秒内结束 → 作为普通工具结果返回（退出码、耗时、输出）。
3. 超过 30 秒 → 工具立即返回 `{ jobId, background: true }`，进程继续运行，登记到该任务名下。
4. 结束 → 生成 `job_done` 输入（03 §5.7）：worker 在一轮中则 steer；空闲则唤醒（系统唤醒优先级）。
5. worker 一轮结束时若还有作业在跑：任务保持"进行中"、继续占名额，不触发"忘记汇报"的提醒（01 §2.3）。
6. 任务进入终态：杀掉其所有作业（不唤醒任何人）。

§5.1 实施（2026-11-10）：生产 bash/powershell 已覆盖，作业事实随任务事件/快照恢复，输出单独落日志。作业与流式 worker 按 taskId 去重占位；占位任务仍可接收原话追加。终态/退出等待进程树清理；启动先完成登记清理，再将遗留 running 作业记 killed/interrupted，不自动唤醒。已结束后台作业的缺失 job_done 输入可补记并去重。服务遵循下列独立生命周期。

### 5.2 服务

1. `service_start` 启动常驻进程，输出写入 `state/jobs/<serviceId>.log`。
2. 登记信息：所属任务、名称、命令、cwd、端口、PID、启动时间。右栏"本地服务"列表与内嵌浏览器起始页展示这些服务（Q20）。
3. 不唤醒 worker、不占名额、不受卡死检测。
4. 生命周期：任务结束后**继续运行**。停止是**控制操作，可直连**：右栏"本地服务"列表与浏览器起始页的"停止"按钮由宿主直接结束进程（不走 worker、不改任务内容），事件流记 `stop{target:"service", source:"user"}`，主 agent 可见。任务内容变更仍必须经主对话的 `task_steer`。
   - 其余停止路径：该任务续接时由 worker 调 `service_stop`；Rally 退出时全部停止。
   - 排队任务取消立即生效（不启动）；运行中先优雅中断，超时升级为进程树强杀（§5.3）。

§5.2 实施（2026-11-10）：服务工具、业务事实/快照/日志、独立进程登记与重启清理已接入；启动后任务终态和 worker 取消不停止服务，退出与用户/所属任务显式停止才回收。用户停止经 shared/ipc 直连，先记审计及 stop 事实，等待整树确认后主聊天通知。主模型动态状态可见运行服务与最近停止服务；无 worker 唤醒输入。工位/浏览器起始页已是真实列表，预览已接 Q20 的 WebContentsView，实际窗口与视觉待用户验收。

### 5.3 进程树终止（Windows）

1. 先 `taskkill /PID <pid> /T`（温和），等 5 秒；
2. 仍在 → `taskkill /PID <pid> /T /F`；
3. 记录结果事件。沿用 Pi `utils/shell.ts` 的 `taskkill` 用法并加上升级（改造计划 7.3）。
4. 可选增强：用 Windows Job Object 把子进程挂到 Rally 名下，Rally 崩溃时系统自动回收（需要原生模块，v1 不做）。

### 5.4 孤儿进程

Rally 崩溃时，Windows 不保证自动清理所有后代。`state/processes.json` 记录每个受管宿主的 PID 与**进程创建时间**；启动时逐个核对，PID 与创建时间都对得上才杀，避免误杀复用了同一 PID 的无关进程。

实施（2026-11-10）：已接入主/worker Git、grep/find、worker shell 作业、服务与 MCP stdio。独立隐藏宿主的 PID＋Windows UTC ticks 创建时间先以临时文件 fsync/rename 登记，成功后才经 IPC 启动命令；宿主保留至管理端整树清理，避免父进程在登记前崩溃导致命令无归属。登记不保存命令、环境或凭据。取消/恢复按 §5.3，普通完成与显式命令 timeout 立即清理；PowerShell 持有原进程句柄直到终止核验结束，防 PID 在检查与 taskkill 间复用，机制参照 [Windows 进程对象与标识符寿命](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_information)。身份不同/原进程不存在只记跳过；终止结果先记 process_stopped 再移除登记。失败保留登记并拒绝新命令，Supervisor 退出继续持锁。

MCP stdio 的双向管道支持背压，关闭先发送 EOF，再触发整树终止并等待完成；初始化/配置取值阶段也能取消，登记后取消不会再启动实际命令。Windows .cmd 启动器通过 cross-spawn 保留参数边界。MCP env/header/OAuth clientSecret 的命令取值也在登记宿主执行，10 秒截止、1 MiB 输出上限；不将配置值写入登记。OAuth 登录与刷新等待异步设置，关闭中止正在取值的命令，已发出的刷新则等待新令牌保存，避免丢失轮换结果。搜索保留 Pi 参数/解析/截断及默认二进制准备行为，缺失工具的下载/探测/解压在独立受管 helper 内运行，PI_OFFLINE 测试不下载。grep 命中结果上限和 grep/find 取消均等待树清理。此路径仍未覆盖 Pi 模型/鉴权等其他配置命令、任意第三方会话挂死或主动脱离可发现父子链的进程，不等于完整进程管理完成。

## 6. 持久化（D1/D3 细化）

| 数据 | 文件 | 写者 | 说明 |
| --- | --- | --- | --- |
| 事件流 | `state/events-*.jsonl` | Supervisor 单写者 | 全局单调 `seq`；先落盘再广播；按大小分段 |
| 任务快照 | `state/snapshot.json` | 同上 | 定期写（如每 200 个事件或 30 秒），带 `snapshotSeq` |
| 审计 | `state/audit.jsonl` | GateService | 只追加，界面没有删除入口 |
| 主会话 / 任务会话 | `agent/sessions/**.jsonl` | Pi | 模型上下文；与事件流各司其职 |
| 记忆 | `memory/MEMORY.md` | 主 agent 工具与用户 | 用户手改后，下一轮重新读取 |

- **只落盘事实，不落盘流式增量**【建议默认】：`message_update`、`tool_execution_update` 这类流式片段只广播、不写事件流；落盘的是开始、结束、结果。这样事件流不会被流式输出撑大，重放结果依然完整。
- 实施（2026-11-10）：事件默认每 20 MiB 轮转（单条过大不拆），加载按编号检查缺段与连续 seq；旧段保留，失败写回滚、回滚失败停止写入。损坏记录保留且提示，缺口/重复/无效信封拒绝恢复。当前历史仍全量内存加载。TaskStore 已接 snapshotSeq 重放缓存（每 200 事件/30 秒/退出保存），只缓存已提交事件的最新状态及保序记录；校验失败回退全量重放。主会话也已接 20 MiB/本段新增 10 次压缩的物理轮转，保留最新上下文、前段链接与跨段引用（01 §6.3）；状态目录独占锁见 §7；完整进程恢复仍待做。
- `chat_search` 的数据来源：事件流中的 `chat_message`。v1 启动时在内存建索引；历史很大时再考虑 SQLite FTS（保留 D1"后续可换 SQLite"的接口）。

## 7. 启动与恢复顺序

1. Electron `requestSingleInstanceLock()`；第二个实例把参数转交已运行实例后退出（改造计划 7.3）。
2. 锁定 `~/.rally/state/`，防止两个进程同时写。已实施：node:sqlite 的 `writer-lock.sqlite` 保持独占事务；Supervisor 构造恢复前获取，真实路径别名共用，失败拒绝启动。文件永久保留、不按时间抢占；进程退出释放 OS 锁，数据库不存业务数据。机制依据 [SQLite 事务锁](https://www.sqlite.org/lang_transaction.html) 与 [Node DatabaseSync](https://nodejs.org/download/release/v24.11.1/docs/api/sqlite.html)。
3. 载入快照，重放 `seq > snapshotSeq` 的事件。
4. 清理所有已登记孤儿宿主（Git/作业/服务/MCP/搜索，§5.4）。
5. 正在进行的运行标记为 `interrupted`，进行中的工具调用记为"结果未知"（01 §4.9）。
6. 启动调度器、中继队列、看门狗。
7. 打开主会话最新的物理分段。
8. 若有中断任务：用一条 `interrupted` 中继唤醒主 agent。
9. 界面就绪。

实施（2026-11-10）：退出时关闭 IPC 入口，同时等待已受理请求、原生浏览器/终端、受管进程及主/worker 会话关闭，最后保存快照并释放锁；不能先等待可能依赖 MCP 关闭的停止请求，再开始关闭会话。构造失败清理半建计时器，启动失败完成收尾；事件/审计/快照在生命周期结束后拒绝再写。关闭错误汇总后保持状态锁到进程退出。全部已登记宿主的恢复先于 main.start、运行中断恢复和调度。锁专项已用真实 Windows 子进程验证竞争/强制终止恢复，并与项目 Electron 的 Node 模式互斥；进程宿主还验证构建文件及 ASAR 内的 Electron Node 模式执行/崩溃恢复。Electron 窗口退出与错误提示待用户验收。

应用退出守卫（2026-11-10）：`ApplicationShutdown` 统一普通退出与启动失败，幂等启动 `shutdown-guard-host` 并确认就绪后才调用可能阻塞的清理。临时守卫不写业务状态，独立计时 60 秒；到期核验主进程 PID/创建时间并通过 §5.3 的 Windows 句柄核验路径立即强杀整树。正常收尾完成后取消守卫并 `app.exit`，已进入终止阶段则不再被取消打断。此截止只作用于应用退出，不改变 Q12 的单任务无上限规则。正常关闭等待 OAuth 刷新落盘；强制退出时未完成的凭据/其他写入可能中断，仅保证沿已有已提交事实和进程登记恢复，不作完整保存承诺。

主进程还有 75 秒本地异步兜底，守卫启动失败或退出时仍可结束异步挂起；它无法处理同步阻塞。独立守卫保护的是成功就绪之后的收尾阻塞，退出请求处理前主进程已经阻塞、未迁移的配置命令、权限变化/脱离父子链和非 Windows 平台仍属缺口。真实子进程已验证 Promise 挂起、同步死循环、启动失败与正常退出、锁释放及重启恢复；最终构建和 ASAR 的 Electron Node 模式各通过一例，未启动 Electron UI 验收。
