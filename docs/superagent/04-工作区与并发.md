# 04 工作区与并发

- 依据：[00-问答记录.md](00-问答记录.md) Q2/Q5/Q6/Q12/Q14/Q21，改造计划 C4/C6、D1/D3、第 7–8 节，dsh `docs/003-execution.md`（worker 槽位、后台作业、重启）
- 范围：目录模型、写锁、调度与名额、worker 会话生命周期、后台作业与服务、持久化布局、启动与恢复。

## 1. 目录模型

四类目录，各管各的：

| 目录 | 是什么 | 谁写 | 来源 |
| --- | --- | --- | --- |
| 当前项目 | 标题栏选中的目录，只是**默认值**；可在最近项目列表里切换 | 改写任务 | Q5 |
| 默认工作区 | `~/rally`（设置可改），未打开项目时任务落在这里；沿用原型的 `notes/ reports/ repo/` | 任务 | Q5 |
| 任务产出目录 | `<默认工作区>/outputs/<taskId>-<slug>/`，每个任务一个，用户可直接浏览 | 该任务 | Q6 |
| Rally 状态目录 | `~/.rally/`：会话、事件、审计、记忆、作业日志 | 只有系统 | C4 |

```text
~/.rally/                              # 与 ~/.pi 并存（C4）
├─ agent/                              # Pi agent 目录（piConfig 改名后，改造计划 7.2）
│  ├─ settings.json  models.json  auth.json  mcp.json
│  ├─ skills/  extensions/  prompts/  themes/
│  └─ sessions/
│     ├─ main/0001-<ts>.jsonl …        # 主会话物理分段（Q11）
│     └─ tasks/T-1045.jsonl …          # 每个任务一个会话文件（Q5 派生 7）
├─ state/
│  ├─ events-0001.jsonl …              # 全局 seq 事件流，按大小分段（D3）
│  ├─ snapshot.json                    # TaskStore 快照
│  ├─ audit.jsonl                      # 审计，只追加
│  ├─ processes.json                   # 作业/服务的 PID 与进程创建时间（孤儿清理用，§7）
│  └─ jobs/J-3.log  S-2.log …          # 作业与服务的输出
└─ memory/MEMORY.md                    # 记忆（Q23）

~/rally/                               # 默认工作区（Q5）
├─ notes/  reports/  repo/
└─ outputs/T-1045-landing/ …           # 任务产出目录（Q6）
```

日志沿用改造计划 7.2：`%LOCALAPPDATA%\Rally\logs`。Electron 自身数据（窗口状态、浏览器缓存）放在 `%APPDATA%\Rally`。

- 主会话的 cwd 固定为 `~/.rally/agent/main/`，不随项目切换（Q5 派生 2）。
- worker 的 cwd＝任务 cwd；Pi 按它加载 `AGENTS.md` 与项目内 `.rally/`（项目内扩展需先信任项目，附 A3）。

## 2. 写锁（Q2）

### 2.1 锁的键

- 任务 cwd 位于某个 git 工作树内 → 锁键＝**该工作树根目录**；否则锁键＝cwd 本身。【建议默认】
  - 理由：同一仓库的两个改写任务即使目录不同（`web/` 与 `api/`），也会争用 git 索引、根目录依赖安装、测试结果。用户在 Q2 已接受"同一项目的改代码任务不能真并行"的代价。
- 两个锁键冲突：其中一个在**路径段边界**上是另一个的前缀（`C:\proj` 与 `C:\proj\web` 冲突，与 `C:\proj2` 不冲突）。

### 2.2 持锁区间

| 时刻 | 写锁 |
| --- | --- |
| 待批准、排队中 | 不持有 |
| 运行开始（调度放行） | 获取（与名额一起原子分配） |
| 进行中、等待门的决定 | 持有 |
| `blocked`、等用户回答（空闲） | **继续持有**（Q2 派生 4），界面显示"T-1046 等待 T-1045（需处理）释放写入" |
| 中断（重启后未续跑） | 继续持有，直到续跑或取消 |
| 终态 | 释放 |

- 只读任务不申请写锁（Q6）。
- 每个任务只有一个锁键，放行时一次性取得，不存在"占着一把锁等另一把"→ 不会死锁。

### 2.3 Windows 路径规范化

用于锁键、只读检查、访问痕迹，规则统一：

1. `path.resolve` 得到绝对路径；`/` 统一为 `\`；盘符大写；去掉末尾 `\`（根目录除外）。
2. 用 `fs.realpathSync.native` 解析 junction 与符号链接，防止通过链接绕过锁。
3. 比较时大小写不敏感（键统一转小写存储）。
4. 去掉 `\\?\` 前缀再比较；UNC（`\\server\share`）、`\\wsl$\` 按普通路径处理。
5. 路径超过 240 字符时，实际文件操作加 `\\?\` 前缀（改造计划 7.3）。

### 2.4 兜底

即使有写锁，也可能有锁管不到的写入（用户在 IDE 里手改、只读任务通过 shell 写入）。由 02 §3.1 的"读后被改检测"兜底。只读任务通过 shell 写了项目目录的，访问痕迹不一定能看到，作为已知局限写进文档（D15：记录不阻断）。

## 3. 调度

### 3.1 放行条件

一个任务可以启动运行，当且仅当：

1. `approval = approved`；
2. `dependsOn` 中的任务全部为 `done`（首次运行；续接不再检查）；
3. 有可用名额（§3.2）；
4. 改写任务：锁键不与任何持锁任务冲突。

队列按"类别优先级 → 进入队列的时间"排序。**排在前面但不能放行的任务不挡后面的任务**（没有队头阻塞，改造计划 5.2）。

### 3.2 名额（C6）

- 上限默认 **2**（设置可调）。
- 占名额：worker 正在一轮中（含挂起在门上的调用），或有后台作业在跑（Q14 派生 3）。
- 不占名额：待批准、排队中、`blocked` 且空闲、中断、终态。
- 优先级（参照 dsh `WorkerSlots`）：

| 类别 | 例子 | 优先级 | 可用额外名额 |
| --- | --- | --- | --- |
| 用户发起的唤醒 | 回答问题、追加要求（唤醒空闲 worker）、续接 | 最高 | ✓ 可以超出上限 1 个 |
| 系统唤醒 | 作业结束唤醒空闲 worker | 中 | ✗ |
| 新运行 | 首次派发 | 普通 | ✗ |

  额外名额的作用：新派发的任务占满名额时，用户仍能立刻继续一个已有任务（dsh："New work therefore cannot prevent a person from continuing an existing Ticket"）。【建议默认】

### 3.3 排队原因与文案

| 原因 | 文案 |
| --- | --- |
| `dependency_failed` | 排队中 · 上游 T-1042 失败，等待处理 |
| `dependency` | 排队中 · 等待 T-1042 完成后开始 |
| `write_lock` | 排队中 · 等待 T-1045 释放 C:\proj 的写入 |
| `capacity` | 排队中 · 等待空闲工位 |

多个原因同时成立时按上表顺序取第一个（01 §3）。

### 3.4 成本说明（沿用改造计划 2）

每路并行 worker 都是一份独立上下文和一路 API 请求；上限调高会线性增加 token 消耗与限流风险。设置页注明"每增加 1 路，约增加一份上下文成本"。

## 4. worker 会话生命周期

| 阶段 | 做什么 |
| --- | --- |
| 创建（首次运行） | 用 Pi SDK 在主进程内创建 `AgentSession`：cwd＝任务 cwd；模型与思考强度＝"任务 agent 模型"设置（Q22）；工具＝02 §3；系统提示词＝03 §1.2；会话文件＝`sessions/tasks/<id>.jsonl`；挂上 Rally worker 扩展（`tool_call` 钩子、汇报工具） |
| 首条消息 | 03 §5.1（原话＋备注＋上游结果） |
| 运行中 | 订阅会话事件 → 转成 Rally 事件（带 `taskId/runId`）→ 先落盘再广播 |
| 空闲 | 一轮结束且没有作业：`blocked`／等回答时释放名额，会话对象保留在内存 |
| 终态 | 取消订阅，释放 `AgentSession`（D2"完成即归档"），JSONL 保留 |
| 续接 | 用同一 JSONL 重新打开会话，模型取当前设置（Q22 派生 2，待 Pi 实测），发续接消息（03 §5.5） |

### 4.1 卡死检测（Q12）

- 每个占名额的运行都有看门狗，记录最后一个事件的时间。
- 10 分钟没有任何事件、且没有后台作业在跑 → `abort` 当前轮，发送卡死重试提醒（03 §5.9），这次不计失败。
- 重试后又 10 分钟无事件 → 运行结束（`endReason=stalled`），任务 `failed`，唤醒主 agent。
- 没有预算上限（Q12）；用量实时显示（`usage_updated`）。

### 4.2 模型调用失败（附 A8）

网络错误与 HTTP 408/429/5xx：按 2s、4s、8s 退避自动重试 3 次（Pi 若已有自动重试则沿用，不重复叠加）。仍失败 → 任务 `failed`，唤醒主 agent。

## 5. 后台作业与服务（Q14）

### 5.1 作业

1. `bash`/`powershell` 启动子进程，输出同时写入 `state/jobs/<jobId>.log` 和内存环形缓冲。
2. 30 秒内结束 → 作为普通工具结果返回（退出码、耗时、输出）。
3. 超过 30 秒 → 工具立即返回 `{ jobId, background: true }`，进程继续运行，登记到该任务名下。
4. 结束 → 生成 `job_done` 输入（03 §5.7）：worker 在一轮中则 steer；空闲则唤醒（系统唤醒优先级）。
5. worker 一轮结束时若还有作业在跑：任务保持"进行中"、继续占名额，不触发"忘记汇报"的提醒（01 §2.3）。
6. 任务进入终态：杀掉其所有作业（不唤醒任何人）。

### 5.2 服务

1. `service_start` 启动常驻进程，输出写入 `state/jobs/<serviceId>.log`。
2. 登记信息：所属任务、名称、命令、cwd、端口、PID、启动时间。右栏"本地服务"列表与内嵌浏览器起始页展示这些服务（Q20）。
3. 不唤醒 worker、不占名额、不受卡死检测。
4. 生命周期：任务结束后**继续运行**。以下情况停止：用户在主对话里要求（主 agent 没有停服务的工具，所以由一个续接或新任务的 worker 调 `service_stop`）；该任务续接时由 worker 自行管理；Rally 退出时全部停止。

> 待定细节：用户在右栏直接停止服务是否算"任务交互"（Q18 只说任务页不做交互）。【建议默认】服务列表提供"停止"按钮，因为它只结束一个进程，不改变任何任务，而且原型的浏览器起始页本来就展示服务。若不同意，就改为通过主对话停止。

### 5.3 进程树终止（Windows）

1. 先 `taskkill /PID <pid> /T`（温和），等 5 秒；
2. 仍在 → `taskkill /PID <pid> /T /F`；
3. 记录结果事件。沿用 Pi `utils/shell.ts` 的 `taskkill` 用法并加上升级（改造计划 7.3）。
4. 可选增强：用 Windows Job Object 把子进程挂到 Rally 名下，Rally 崩溃时系统自动回收（需要原生模块，v1 不做）。

### 5.4 孤儿进程

Rally 崩溃时，Windows 不会自动杀子进程。`state/processes.json` 记录每个作业/服务的 PID 与**进程创建时间**；启动时逐个核对，PID 与创建时间都对得上才杀，避免误杀复用了同一 PID 的无关进程。

## 6. 持久化（D1/D3 细化）

| 数据 | 文件 | 写者 | 说明 |
| --- | --- | --- | --- |
| 事件流 | `state/events-*.jsonl` | Supervisor 单写者 | 全局单调 `seq`；先落盘再广播；按大小分段 |
| 任务快照 | `state/snapshot.json` | 同上 | 定期写（如每 200 个事件或 30 秒），带 `snapshotSeq` |
| 审计 | `state/audit.jsonl` | GateService | 只追加，界面没有删除入口 |
| 主会话 / 任务会话 | `agent/sessions/**.jsonl` | Pi | 模型上下文；与事件流各司其职 |
| 记忆 | `memory/MEMORY.md` | 主 agent 工具与用户 | 用户手改后，下一轮重新读取 |

- **只落盘事实，不落盘流式增量**【建议默认】：`message_update`、`tool_execution_update` 这类流式片段只广播、不写事件流；落盘的是开始、结束、结果。这样事件流不会被流式输出撑大，重放结果依然完整。
- `chat_search` 的数据来源：事件流中的 `chat_message`。v1 启动时在内存建索引；历史很大时再考虑 SQLite FTS（保留 D1"后续可换 SQLite"的接口）。

## 7. 启动与恢复顺序

1. Electron `requestSingleInstanceLock()`；第二个实例把参数转交已运行实例后退出（改造计划 7.3）。
2. 锁定 `~/.rally/state/`（锁文件），防止两个进程同时写。
3. 载入快照，重放 `seq > snapshotSeq` 的事件。
4. 清理孤儿作业与服务（§5.4）。
5. 正在进行的运行标记为 `interrupted`，进行中的工具调用记为"结果未知"（01 §4.9）。
6. 启动调度器、中继队列、看门狗。
7. 打开主会话最新的物理分段。
8. 若有中断任务：用一条 `interrupted` 中继唤醒主 agent。
9. 界面就绪。

## 8. Pi 落地点（【推断】，待实测）

| 需求 | 预期做法 | 待验证 |
| --- | --- | --- |
| 同进程多会话 | SDK 创建多个 `AgentSession` | 全局单例、`process.chdir`、共享设置对象 |
| 会话文件位置 | 为每个会话指定文件路径 | SDK 是否允许指定会话文件，而不是按 cwd 编码目录 |
| 中途注入（steer） | 会话 API | 注入时机是否为"当前工具调用结束、下一次模型调用之前" |

| 工具结果流式输出 | `onUpdate` | 作业转后台后，原工具调用能否先返回、进程继续 |
