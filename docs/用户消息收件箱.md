# 用户消息收件箱与队列

## 日常行为

桌面、云端客户端、飞书和 QQ 共用一份收件箱。消息及附件引用先写入执行主机的事件日志，接收成功后才交给主 Agent。忙时继续接收，按接收顺序逐条处理，每条消息拥有独立的一轮回复。桌面不再把新消息作为 steer 插入正在运行的用户轮次。

- 主对话中的用户气泡下显示排队、处理中、未完成或已撤回；完成后收起普通状态，不另加大面板。
- 忙时仍可发送；有草稿时发送按钮与停止按钮同时可用。未开始的消息可撤回，原文保留但不再处理。
- 停止会中止当前回复，并暂停后续消息队列。点击“继续队列”或发送新消息后继续；被中止的那一条单独标为未完成，需要明确重试，不会自动重跑。
- 模型最终报错会保留原因并暂停队列，避免逐条撞同一个故障。已有供应商层的有限重试保持原规则，收件箱不增加自动模型重试。
- 没有可用模型时先保存并等待配置。模型恢复后接着处理。
- 整理上下文保留收件箱；新建会话前要求处理或撤回未完成的输入，以及发送或取消未完成的 IM 回传，防止重置丢消息。

当前实现不合并连发消息、不判断优先级，也不把队列长度、状态或到达时间动态塞入模型上下文。用户可以用停止按钮中止当前轮，再撤回或重试具体消息。

## 重启、重复投递与中断

`chat_message` 的首次写入同时包含原文和 `delivery.status=queued`，没有“已显示但未加入队列”的中间步骤。状态更新仍使用同一消息 ID，附件保留引用也复用现有资源库。

- 尚未开始的消息在正常启动后继续排队；手动暂停状态跨重启保留。
- 原先标为 processing 的消息恢复为 failed，提示可能已有部分操作完成，并暂停后续队列。用户明确重试时携带一次性恢复说明，要求先核对历史和任务、接续未完成工作。不能保证未知结果的外部操作恰好执行一次，所以不自动重放进行中的请求。
- IM 按平台、应用、会话和原消息 ID 去重；应用内历史重置后也不会因平台重投再次执行已接收的消息。
- 云端请求继续校验设备、请求 ID 和内容摘要，持久收件箱再按设备与请求 ID 去重。新版请求在接收成功但 HTTP 回执丢失后可以安全重试；旧版无法判定是否已接收的历史请求维持原先“先核对聊天记录”的提示。
- 旧聊天记录没有 delivery 字段，按历史消息读取，不会在升级后重新执行。

## IM 回复

连接器收到消息后等待持久接收，不占住 SDK 的处理回调等待模型。回复文字与回传状态写在对应收件箱记录，完成后只回到原来的 IM 消息。后台 Worker 通知和后来的桌面轮次不会被当成该消息的回复；IM 轮次中暂缓注入任务中继，之后沿用原有中继流程。

断线时保留待回传内容，原账号重连后再尝试。发送前校验原应用与配对账号，换绑后不会投递到新账号。飞书记录原发送者，QQ 私聊目标即配对账号。

平台发送失败会在原用户消息下显示原因，可“重发回复”或“取消回传”。重发使用已保存的文字，不重新调用模型。进程在发送途中退出时，发送结果标为不明，需要先检查原聊天再重发，避免自动重复。QQ 平台可能拒绝过晚的被动回复，此时完整结果仍留在 Rally。运行中每 15 秒只检查本地队列与连接状态，没有新增轮询模型或持续调用平台。

## 与现有功能的关系

- 72 小时闲置保护优先于队列和回传；重启、读取队列、点击继续/重试和重复 IM 投递都不算新发言。新消息到达才续期。闲置中断的主 Agent 消息遵守上述未完成处理规则，Worker 的原运行接续规则保持不变。
- `chat_search`、原话授权和教练输入排除尚未交给模型或已撤回的消息，避免排队消息提前影响当前任务。历史已开始的请求仍可用于核对已有操作。
- Assistant 输出记录 `replyTo`；Worker 的 `context` 按实际消息与对应回复配对，排除排队、撤回和失败轮次，避免“后到的用户消息抢走前一条回复”。
- 用户消息使用新队列；Worker 名额队列、中继持久队列继续各管各的。停止主回复暂缓中继唤醒，继续队列或新发言后恢复。
