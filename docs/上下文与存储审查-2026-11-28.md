## PR #10 的结论

历史搜索确实修复了新建会话后无法检索旧消息的问题：从事件日志按消息 ID 取最新版本，再用内存中的消息覆盖；UI、当前模型会话、原有授权边界未变。recentEnded 和 capability catalog 的缩减能降低日常开销，但与本次数十 MB 的审批清单不是同一问题。

没有发现需要阻止该搜索实现合入的代码回归。审查阶段先保留 PR；现已在 `a52ef46` 部分采纳并关闭 PR #10。

需要澄清一项工具契约：`chat_search` 可以返回新会话之前的用户消息，但 `MainAgent.quote()` 仍仅接受当前会话的用户消息；`task_dispatch` 等调用 `freezeQuotes()` 时会返回 QUOTE_INVALID。这是已有设计边界，`rally-supervisor.test.ts` 的 “starts a fresh main conversation without losing memory, tasks, or restart continuity” 明确断言旧 ID 不能引用，不能擅自改为允许旧授权。PR 新增的工具描述和返回值应说明历史可搜索不代表可用于新授权，避免模型反复搜索同一个不可引用 ID。

源码入口：`src/main/supervisor/main-agent.ts` 的 search/searchHistory/quote；`src/main/supervisor/chat-search.ts`；`src/main/supervisor/task-quotes.ts`。

## 修复前复现记录，按优先级排序

### P1：批量删除将越来越大的完整任务反复落盘

链路：`file-delete.ts` 每删除一个条目调用 `TaskStore.recordAccess()`；它追加访问记录后又调用 `recordChangedFiles()`。后者同时写入完整 task（含 changedFiles）与完整 files 数组。因此累计日志体积近似随文件数平方增长，审批清单改为文件引用后仍然存在。

不实际删除文件，只用 400 条合成 fs_delete 记录复现：200 条时事件文件共 3,451,576 字节；400 条时 13,381,376 字节，文件数量翻倍、日志增长 3.88 倍。未按此比例对 4.5 万个文件做生产测试。

修复方向：以已有 access_recorded 增量记录作为持久依据，避免每个条目再保存完整任务；保留崩溃后 changedFiles 的重建语义，UI 更新可合并。不得为减少日志丢弃逐文件的删除事实。现有 replay 已从访问记录重建 changedFiles，可优先复用。

源码入口：`src/main/supervisor/task-store.ts` 的 recordAccess、recordChangedFiles、commit、replay；`src/main/supervisor/file-delete.ts` 的删除循环。

### P1：动态快照在压缩判断之后注入

`AgentSession._compactBeforeNextAssistantResponse()` 以会话持久投影估算阈值；Rally 在随后调用的 `agent.transformContext` 中加入 rally-state、memory、capabilities 等动态快照。这些新内容不在本次发送前的投影中。

用 faux 模型设置 4,096 token 窗口，短会话后在 transform 中插入 200,000 字符。provider 收到 200,007 字符，收到请求之前 compaction_start 次数为 0。这证明动态内容可以绕过本次发送前检查，不代表任何自动压缩都没有作用。

此外，大型单条 relay 已写入历史时，即使触发自动压缩，摘要请求也会把待压缩内容串成正文发给模型；源码中不是按窗口逐块归纳。因此超大消息不能依赖事后压缩救场。

修复方向：动态快照必须自身有明确总预算，发送前应按实际模型输入计数；持久大结果在进入会话之前落盘并返回可定位摘要。不能简单重复调用压缩，因为动态快照会再次注入。

源码入口：`packages/coding-agent/src/core/agent-session.ts` 的 _exceedsCompactionThreshold/_compactBeforeNextAssistantResponse；`packages/agent/src/agent-loop.ts` 的 streamAssistantResponse；`src/main/supervisor/main-agent.ts` 的 transformContext；`packages/coding-agent/src/core/compaction/compaction.ts` 的 generateSummaryWithUsage。

### P1：普通 MCP 审批与 Worker 提问没有内容预算

普通 MCP 的不可逆操作把完整参数交给 GateService，modelGate 原样返回普通审批，Relay.render 也直接 JSON.stringify。当前热修复只处理 file_delete。

合成 MCP 参数正文 1,050,000 字节后，rally-state 为 1,051,167 字节，中继事件约 1,050,750 字节。无真实 MCP 服务或外部写操作。

Worker 的 task_report.summary/question 没有长度上限。汇报中继虽然截取 summary 前 600 字，但 question 原样进入中继及每轮 rally-state。合成 1,000,000 字符问题后，快照约 1 MB。正常模型生成的长度通常受输出上限约束；代码本身没有可依赖的宿主限制。

修复方向：一般审批需要一致的体积策略，保持完整授权证据可查，不允许根据被截断的参数放行；Worker 提问应限定可直接展示的长度，详细材料通过结果文件引用。不要静默删掉风险信息。

源码入口：`src/main/supervisor/mcp.ts`、`gates.ts`、`gate-tools.ts`、`relay.ts`、`rally-state.ts`；`tools.ts` 的 reportSchema。

### P1：task_read 的分页没有约束 changedFiles

files 视图只分页 accesses，仍带完整 changedFiles；report 视图同样带完整 changedFiles。因此降低 limit 对该字段无效，而且翻每页都会再次带回全量清单。

10,000 条合成文件路径、limit=1 时，files 返回 1,199,743 字节，report 返回 1,198,950 字节。

修复方向：变化文件也单独分页，摘要视图只返回总数和有限示例；对单条 report、input、command 等还需要字节预算或文件引用，仅分页条目数量不能限制一条大记录。

源码入口：`src/main/supervisor/task-read.ts` 的 report/files/runs/inputs 等分支；`docs/Prompt/tools-Description/tasks.md` 当前只承诺条数分页。

### P1：删除工具预览与失败结果仍可能很大

dryRun 的 preview 只保留 50 项，但 outsideCwd 和 uncommitted 是完整数组；中途失败后 failed 为每个未执行目标追加记录。当前审批热修复不处理这些工具结果。

600 个目录外文件及父目录：preview 为 50 条，但 outsideCwd 为 601 条，返回内容 119,814 字节；更多文件可继续线性放大。失败路径由源码确认，本轮未对生产目录制造删除失败。

修复方向：大结果全文落盘，返回准确总数、有限示例和可按需读取的路径；保持成功删除与失败、未执行目标的可核验记录。

源码入口：`src/main/supervisor/file-delete.ts` 的 preview、failed 构建与 outputResult。

### P2：定时任务列表及创建/修改回执重复返回全部冻结背景

schedule_list 无分页，直接序列化全部计划，每项包含原话、note、context。schedule_create/update 回执也返回完整计划。

10 个计划各保存合法的 60,000 字符背景时，列表返回 614,491 字节；相同数据的自动 rally-schedules 摘要只有 1,905 字节。风险主要在工具结果，不应误称自动计划快照同样无界。

修复方向：列表按页返回摘要和等待状态，按 ID 查看计划要求/背景；创建修改回执返回 ID、revision、时间、背景计数，避免把已知大背景再次回传。

源码入口：`src/main/supervisor/schedule-tools.ts`，`schedules.ts` 的 list/context。

### P2：记忆文件外部编辑可绕过注入预算

memory_add/edit 的写入路径检查 USER 3,000 字节等预算，但 MemoryStore.snapshot 只拒绝大于 1 MiB 的文件；context 将外部修改后的完整正文注入每轮。

手动写入 500,000 字节 USER.md 后，context 返回 500,548 字节，未提示不可用。三个文件同时变大时影响累加。Worker 冻结记忆已有预算检查，与主助手注入行为不一致。

修复方向：主助手读取并注入记忆时也检查预算，给出明确的超限状态和文件位置；保留原文，不自动覆盖或假装完整注入。教练的 notebook 读取也要同步检查。

源码入口：`src/main/memory-store.ts` 的 context/snapshot；`src/main/supervisor/task-context.ts`；`coach.ts` 的 notebook。

## 修复前热修复自身的启动风险

1. GateService 构造函数迁移所有历史审批，compactDeleteGate 可能抛错且没有逐条降级。合成 1,000 条较长根路径的旧审批，摘要仍超过 64 KiB，抛 DELETE_GATE_TOO_LARGE。即使是已经拒绝的历史审批，也可能阻断整个 Supervisor 启动。
2. compactDeleteRelay 用正则查找整段消息中的 gate_request 标签，再对紧接的一行 JSON.parse。Worker 问题里恰好包含该格式示例、且整个 relay 超过阈值时，也会被误解析。合成约 70 KB 的问题含 `not JSON` 示例，函数抛 SyntaxError；repairDeleteGateContext 在主会话创建前调用，可能导致主会话恢复失败。

修复方向：旧数据迁移应保留历史证据、失败时可隔离并明确提示，不能让一个已结束的审批拖垮启动；应按宿主结构化中继记录处理，不能在任意正文中把同名标签当成可信结构。当前生产会话已恢复，本轮未改生产来复现这些异常。

## 审查补充的边界路径（修复及保留策略见上文）

以下为静态审查发现，未声称均已实际触发：

- Relay.flush 一次聚合所有待投递事件；单条有限仍可能累计超过模型窗口。
- rally-state 的所有未结束任务、scope、依赖、问题、运行中服务没有总体积预算。PR 只减少 recentEnded。
- Coach 把窗口内所有 schedule_changed 事件直接序列化，其中重复包含全量计划背景；单条超长用户消息不会被 transcript 的“保留最后一条”逻辑截短；idea 的 evidence 也可能重新附上完整消息正文。
- 20 MiB 的事件分段是文件轮转，不是历史总量上限。EventLog 启动时仍读取所有事件；热修复保留了已有大事件，因此不会自动收回它们占用的磁盘。
- 主会话 compaction_end 处理没有展示 event.errorMessage；只看 UI 难以区分没有触发与触发后失败，应保留可诊断的失败原因。

## 已有约束，不应误报为完全无界

- MCP 工具普通文本结果由 limitMcpContent 限制为约 20 KiB，并保留完整结果位置；这不约束 MCP 的审批参数，也不意味着结构化存储一定很小。
- Worker 完成汇报中继的 summary 最多 600 字、变化文件示例最多 6 项；任务工具读取完整 report 是另一条路径。
- capability catalog 有总字符预算；身份和角色配置有字段/数量约束。
- rally-schedules 自动快照最多 50 个计划且不含冻结 context。
- 任务背景聊天本身每条最多 4,000 字、总计 60,000 字；记忆复制检查已有预算。
- fetch_page 默认正文 20,000 字符、允许显式调整至 100,000；HTTP 正文返回最多 20,000 字符；SSH 输出最多 24,000 字符；这些是已有明确限制，不是此次无上限审批清单。
