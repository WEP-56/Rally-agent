# 测试清单 · 提供商配置与模型选择器（M1-C）

> 目标：配好主 agent 和任务 agent 两个全局模型，确认「设置 → 选择器 → 实际请求 → 任务派发/汇报 → 重启保留」链路。开发状态见 [开发实施 TODO](开发实施TODO.md)。
> 标 ★ 的条目是**必过项**；任何一条 ★ 不通过，M1-C 就不能算完成。

## 0. 前置准备

- 启动：`npm run dev`（仓库根目录 `D:\Rally-agent`）。
- 需要：至少一个真实可用的模型服务（Base URL + API Key + 模型名）。没有的话只能验配置与选择器，沾「真实回复」的条目会失败。
- 配置文件路径（明文 JSON，重启后仍在这里）：

```text
C:\Users\<你的用户名>\.rally\agent\rally-models.json
```

- 配置文件的形状（照此填写即可，也可直接用设置页生成）：

```json
{
  "version": 1,
  "active": { "provider": "rp_xxx", "model": "your-model", "thinkingLevel": "medium" },
  "worker": { "provider": "rp_xxx", "model": "your-model", "thinkingLevel": "high" },
  "providers": [
    {
      "id": "rp_xxx",
      "name": "我的供应商",
      "protocol": "messages",
      "baseUrl": "https://api.example.com",
      "apiKey": "sk-...",
      "models": [
        {
          "id": "your-model",
          "name": "Your Model",
          "contextWindow": 128000,
          "compactionThreshold": 0.8,
          "maxTokens": 16384,
          "vision": true,
          "reasoning": true,
          "thinkingLevels": ["low", "medium", "high"]
        }
      ]
    }
  ]
}
```

- 协议字段只有两种值：`messages`（请求走 Anthropic Messages 协议）、`responses`（请求走 OpenAI Responses 协议）。实际 HTTP 由 Pi 实现，Rally 不自写适配。
- 「压缩阈值」目前只作为 Rally 元数据保存与展示，尚未驱动 Pi 的自动压缩（Pi 只按 `contextWindow` 触发压缩）。这是已知边界。

## 1. 单提供商配置成功路径

| # | 操作 | 预期 |
| --- | --- | --- |
| 1 ★ | 打开 设置 → 供应商 → 添加供应商；填名称、协议选 `messages`、Base URL、API Key | 卡片可编辑，字段随输入更新；底部出现「未保存」 |
| 2 ★ | 点「拉取模型」（接口支持时）或直接在「拉取失败时手工填写模型名」里输入模型名后点「添加」 | 模型出现在卡片下方；拉取成功时提示「接口返回 N 个模型…」，失败时提示「拉取失败：…」且手填仍可用 |
| 3 ★ | 展开某个模型的「元数据」，填上下文长度、压缩阈值、最大输出，按需勾「支持视觉/支持思考」，点「保存配置」 | 页面顶部提示「已保存」，无红色错误条；`~/.rally/agent/rally-models.json` 出现并含该供应商 |
| 4 ★ | 打开对话框左下角的模型选择器 | 出现一行浅色小字的供应商名，其下列出该供应商的模型；选中后按钮显示模型名 |

## 7. 真实任务端到端

> 前置：设置 → 供应商分别选择“主 agent 模型”和“任务 agent 模型”（可以相同），各自选择思考档位。两者共用 Rally 供应商配置；任务模型的更改影响之后启动/续接的运行。未选择任务模型时应明确提示前往设置，不能回退 Pi 默认值。旧版“v1 不做双模型／接线需额外批准”的说明错误，已撤回，按 Q22 实施。

| # | 操作 | 预期 |
| --- | --- | --- |
| 21 ★ | 选好两个真实模型，在对话里说：「派发一个任务：让 worker 读取 README 前 20 行并汇报」 | 主 agent 调 `task_dispatch`；主对话出现待批准卡，展示原话、cwd、mode；右栏同步只读状态。目录不明确时先澄清，不拿 SDK README 代替项目 README |
| 22 ★ | 点主对话任务卡的「批准派发」 | worker 用任务模型运行；完成后右栏为完成并带汇报，主对话出现系统行与主 agent 的结果转述 |
| 23 | 派发耗时任务，运行中在主对话说「取消 T-…」 | 主 agent 调 `task_cancel`，引用该用户消息；任务中断、不自动重跑，晚到汇报不能覆盖取消状态；右栏不提供取消按钮 |
| 24 ★ | 打开“自动批准”，再派发任务；同时保留之前一张待批准卡 | 新任务自动开始，旧待批准任务保持待批准；重启后开关恢复 |
| 25 ★ | 任务完成后换一个任务模型，再说「续接 T-…，……」 | 同一任务和 JSONL 新增一次运行，使用新任务模型；按当前全局审批模式重新审批 |
| 26 | 运行中切换任务模型/思考档位 | 当前 worker 保持原模型/档位；之后启动的任务才改变 |
| 27 | 只选择主模型，清空任务模型后派发 | 任务明确失败，提示在设置 → 供应商选择任务模型；主对话可见失败，不无限等待 |
| 28 | 让只读任务尝试用 `write/edit` 改项目文件，再写产出目录 | 项目写入被拒，产出目录写入成功；不把失败写入记成 changedFiles。shell 不是文件沙箱，仍受提示词纪律约束 |
